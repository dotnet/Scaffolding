# Identity API scaffolding: baseline and next steps

`dotnet scaffold aspnet identity-api --project MyApi.csproj --dataContext ApplicationDbContext --dbProvider sqlite-efcore` adds editable Identity API endpoints to an existing .NET 10 or .NET 11 web project with top-level `WebApplication` startup in `Program.cs`. Use `--prerelease` when the target framework requires prerelease EF Core packages. The command adds an Identity user and EF Core context if needed, installs the Identity EF and database-provider packages, adds a connection string, registers Identity API services and authorization, and maps the endpoints under `/identity`. It writes `IdentityApi/IdentityApiEndpoints.cs` and preserves edits on subsequent runs unless `--overwrite` is specified. Existing user and context types are preserved even with `--overwrite`; an existing `IdentityDbContext<TUser>` determines the user type. Existing `AddDbContext<TContext>` registrations and connection strings are retained. Create and apply EF Core migrations, and replace the default no-op email sender before using registration, confirmation, or password reset in production.

The endpoint implementation is adapted from [`dotnet/aspnetcore` `release/11.0` at `ec5a3b4`](https://github.com/dotnet/aspnetcore/blob/ec5a3b43a7186a2a14d88695e7b8e435797f6a0f/src/Identity/Core/src/IdentityApiEndpointRouteBuilderExtensions.cs). The corresponding [`release/10.0` implementation at `55d77e1`](https://github.com/dotnet/aspnetcore/blob/55d77e1e0349aa2a079a516f6ecb7c79b56bf85c/src/Identity/Core/src/IdentityApiEndpointRouteBuilderExtensions.cs) has the same source, so both targets share a template. The class and extension method are renamed to `ScaffoldedIdentityApiEndpointRouteBuilderExtensions.MapScaffoldedIdentityApi` to avoid colliding with the framework method; handlers, routes, HTTP contracts, and security checks are otherwise unchanged. The framework supplies the request/response DTOs, token handling, and `AddIdentityApiEndpoints<TUser>` service registration. The generated source retains the upstream MIT license header and includes its license in `IdentityApi/LICENSE.txt`.

The command deliberately does not remap an existing `MapIdentityApi` installation or mix a new registration with existing Identity UI services: first remove its `MapIdentityApi` and Identity service registration calls, then scaffold, and reconcile the service configuration. An incompatible non-Identity context is rejected before installing packages or writing files. No account data is migrated automatically.

## Test coverage

An offline SHA-256 check verifies that the template and both output baselines match the pinned release source after undoing the intentional renaming and attribution comments. `IdentityApiBaselineTests` uses main's shared `ScaffolderBaselineRunner` and `GeneratedProjectBaseline` infrastructure to build the checked-in expected app first, scaffold a copy of the registered `EmptyWebApp` input, build it, and compare every project file. Package version values and text line endings are normalized by the shared comparer. Tests never rewrite checked-in baselines. Focused tests cover copying the source and MIT notice, preserving edits, explicit overwriting, missing templates, and validation.

CLI integration tests scaffold and build .NET 10 and .NET 11 web projects, check startup wiring and packages, and exercise rerun/overwrite behavior. A real Kestrel host with SQLite and a test email sender verifies registration validation, email confirmation, bearer login and refresh, authorized account information, password reset, security-stamp rejection of stale refresh tokens, and cookie login. Additional cases cover custom user/context types, existing database registration, asynchronous startup, and rejection of incompatible contexts or an already-mapped framework API. Tests use temporary project directories and allocated loopback ports; they do not alter global SDK/tool installations or checked-in output.

Run the focused suite with `dotnet test test\dotnet-scaffolding\dotnet-scaffold.Tests\dotnet-scaffold.Tests.csproj --framework net11.0 -p:BuildTfm=net11.0 --filter "Family=identity-api|FullyQualifiedName~IdentityApiScaffolderTests|FullyQualifiedName~IdentityApi_HasSourceAndProgramConfig|FullyQualifiedName~ValidateIdentityStep_ApiScenario|FullyQualifiedName~AddAspNetConnectionStringStepTests"`. CI includes the new family in the Identity integration shard and inventories its options and supported targets. An installed SDK supporting each target and access to the repository's NuGet feeds are required. Baselines and focused integration tests reuse `ScaffoldCliHelper` for execution, project setup, SDK selection, and preview-package arguments. Rejection tests assert a nonzero exit code, the diagnostic, and unchanged files.

## Why source generation

The [original token endpoint proposal](https://github.com/dotnet/aspnetcore/issues/47227) and [HTTP endpoint design](https://github.com/dotnet/aspnetcore/issues/50009) led to the .NET 8 API, intended to make Identity usable by SPA, Blazor, and other first-party clients without Identity UI ([announcement](https://devblogs.microsoft.com/dotnet/asp-net-core-updates-in-dotnet-8-preview-4/)). The bearer tokens are opaque, not JWTs; the API is not intended to be an OAuth/OIDC identity provider. [Community guidance](https://codewithmukesh.com/blog/identity-endpoints-aspnet-core/) also calls out the fixed registration payload and inability to disable `/register` as reasons to own the endpoint source. The proposal below addresses customization **in the scaffolded code**, not by silently changing the framework contract.

## Proposed follow-up improvements

1. **Make registration extensible first.** [dotnet/aspnetcore#50303](https://github.com/dotnet/aspnetcore/issues/50303) asks to collect fields beyond email and password. Generate a local registration request type and an explicit mapping to `ApplicationUser` properties; preserve validation, duplicate-email behavior, confirmation emails, and the current response contract by default. Avoid changing framework-wide DTOs.
2. **Separate login identifier from email.** The baseline sets `UserName = Email` and passes the login `Email` to `PasswordSignInAsync`; [dotnet/aspnetcore#68662](https://github.com/dotnet/aspnetcore/issues/68662) tracks the resulting limitation. Offer a deliberate email-or-username mode, using the corresponding user lookup and preserving lockout, two-factor, and security-stamp checks.
3. **Make endpoint exposure and paths explicit.** [dotnet/aspnetcore#57899](https://github.com/dotnet/aspnetcore/issues/57899) asks to turn off individual routes, especially public registration; [dotnet/aspnetcore#55142](https://github.com/dotnet/aspnetcore/issues/55142) requests route customization. Put route patterns in one place and allow specific handlers to be omitted. Keep a safe default set and test that disabled routes are not mapped.
4. **Document customization boundaries.** Show how to configure named `BearerTokenOptions` (requested in [dotnet/aspnetcore#51047](https://github.com/dotnet/aspnetcore/issues/51047)), plug in a real `IEmailSender<TUser>`, and restrict or customize routes. Do not present opaque tokens as JWTs or add OIDC/social login or a logout API by implication: those require separate designs and security review. Keep the initial scaffold's behavior in sync with its target release branch and add opt-in improvements with contract tests.

Direct Reddit discussions were not independently accessible for verification; the linked issues, source, and blog posts are the evidence for these priorities.
